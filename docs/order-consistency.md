# 주문 상태 일관성

주문 생성, 체결 조회, 재시작 복구는 다음 불변조건을 유지한다.

- 종목 한도는 국내·미국을 구분한 종목 키의 합집합이다. 실제 잔고, 잔고 반영 전 확인된 관리 체결, 미완료 BUY를 포함한다. 부분 체결·추가매수는 중복 계산하지 않고 취소 **요청**만으로 자리를 비우지 않는다. 기존 초과 보유분을 자동 매도하지 않는다.
- 미국 BUY는 송신 직전 다시 조회한 가격이 손절 기준 이하이면 무효다. 가격 하락을 더 싼 매수 기회로 자동 해석하지 않는다.
- 체결 결과는 주문번호 하나로 덮어쓰지 않는다. 종목·방향·주문수량·누적 체결 단조 증가·잔량·가격·종료 상태를 대조한다. 중복 행과 누락 수량은 오류이며 기존 기록을 유지한다. IOC 재주문은 해당 하위 주문 수량을 검증한 뒤 기존 체결과 합친다.
- 이전 거래일 주문에 오늘 주문번호를 대입하지 않는다. 한투 국내 조회는 원주문 날짜와 연속조회 페이지를 사용한다. 키움 국내 당일 API로 과거 체결을 추정하지 않고 명세서 증빙을 요구한다. 해외는 기존 날짜별 증빙 대조를 이용한다.
- 해외 과거 이력이 미완료이면 별도 현재 미체결 조회(KIS `inquire-nccs`, Kiwoom `ust21050`)까지 수집한다. 현재 목록에 없다는 사실만으로 체결·취소·만료를 만들지 않는다. 종료 증빙 부족은 카드에 명시하고 자동 재주문을 막는다. 예전 단독 봇의 날짜 기반 자동만료도 같은 원칙을 따른다.
- 수신 신호의 신선도 기한, 다음 장 주문 계획 기한, 사용자 승인 기한은 별개다. 신선한 신호가 시장 종료로 처음 예약될 때만 기존 다음 장 계획 기한을 설정한다. 승인·명시적 기한은 연장하지 않는다. 재시도와 재시작은 저장된 기한을 줄일 수만 있다.
- 모의계좌에서 **주문 전 조회·상태 확인을 기다리다 만료된 신호**는 기존 대기열의 별도 `REVIEW`로 다음 주문 가능 세션에 재검증한다. 이는 주문 접수나 승인 기한 연장이 아니다. 실제 승인 대기·사용자 취소·정책 차단·이미 주문한 신호는 자동으로 되살리지 않는다. 접수 여부 불명확은 기존 주문 대조로 처리한다.
- 재검증은 세션 시작 후 30분 동안 기존 가격·보유·위험·승인 경로를 다시 거친다. 매수·추가매수는 원 신호부터 최대 5일까지만 검토하고 후속 매수·청산 신호를 확인한다. 청산·익절·부분익절은 조회 장애가 계속되어도 해당 관리 포지션에 묶어 다음 세션 검토를 유지하며, 보유분 종료·다른 진입으로 교체되면 옛 신호를 적용하지 않는다. 대기 작업은 매도를 매수보다 먼저 처리하되 이미 송신 중인 주문을 강제 중단하지 않는다. 실계좌 정책과 검토용 알림의 주문 여부는 바꾸지 않는다.
- 포트폴리오 갱신 실패는 기존 실행기의 작업을 재사용해 1분·5분·15분(이후 15분) 간격으로 재시도한다. 기한을 저장하므로 재시작이 호출 폭주를 만들지 않는다. 새 체결, Discord 장애, 일부 계좌 실패, 웹 연동 실패는 성공한 전체 갱신으로 오인하지 않는다. 계좌 자산 그래프 수집은 별도 작업이다.

## 검증

`npm run self-test`는 네트워크 오류·가짜 증권사 응답·로컬 테스트 서버를 이용한다. 실제 주문을 만드는 검사가 아니다.

주요 회귀 검사는 `tests/account-runtime.test.ts`, `tests/account-executor.test.ts`, `tests/order-tracking.test.ts`, `tests/order-tracker.test.ts`, 두 증권사 client 테스트에 포함한다. 미체결 한도, 손절선 아래 최종 호가, 기한이 긴 옛 예약, 날짜 충돌, 부분 체결, 재시작 후 포트폴리오 복구를 재현한다.

한투 요청 형식은 공식 [일별 주문 체결 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_daily_ccld/inquire_daily_ccld.py)와 [해외 미체결 예제](https://github.com/koreainvestment/open-trading-api/blob/main/legacy/Sample01/kis_ovrseastk.py)를 참고한다. 수신 날짜·수량 검증은 요청 성공 여부와 별개다.

이 검증은 증권사 장애가 다시 발생하지 않는다는 보장이 아니다. 특히 과거 종료 상태가 증권사 API에도 없으면 명세서/원주문 증빙이 필요하며, 자동으로 만료를 지어내지 않는다. 운영 코드를 바꾸면 정책 해시도 달라지므로 변경 전후 성과를 하나의 고정 정책 표본으로 합치지 않는다.
