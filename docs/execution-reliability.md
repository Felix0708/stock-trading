# 신호 복구·계좌별 처리·성과 비교

변경일: 2026-09-07. 원본 지표와 위험예산/Sigma 정책은 변경하지 않았습니다. 실계좌 잠금도 유지합니다.

## 수신과 재시작

인증·본문 크기·JSON 확인 후 원본을 `<WEBHOOK_LOG_FILE>.pending/<requestId>.json`에 먼저 저장합니다. 파일과 디렉터리 동기화가 성공해야 HTTP 200을 반환합니다. 저장 실패는 503이며, 접수 성공으로 표시하지 않습니다.

처리 결과는 기존 JSONL, 전달 완료는 `.delivered`에 기록합니다. 서버 시작 시 수신 원본과 미전달 결과를 읽어 같은 요청 ID로 재처리합니다. 과거 원본은 지표 상태 복원에만 사용하고 이미 전달한 신호를 다시 발행하지 않습니다. 미전달 신호는 기본 24시간까지만 복구하고 그보다 오래되면 `.expired`에 남깁니다. 전달 실패는 30초 주기로 다시 확인하며 `/health`는 실패가 남은 동안 503입니다.

전원 중단 등으로 로그의 마지막 행이 도중에 끊겼다면 정확한 원본 바이트를 `.incomplete-<id>` 파일에 보관한 후 그 미완성 꼬리만 제거합니다. 접수 원본으로 다시 복구하며 완성된 중간 행의 손상은 자동으로 무시하지 않습니다. 처리 결과 저장에 실패한 원본도 기존 이력과 수신 시각 순서로 지표 상태에 반영합니다.

계좌 중립 서버는 현재 위험 게이트를 재평가해 전달하고, 계좌 실행기는 기존 요청 ID/수신 작업/주문 의도 기록으로 중복 송신을 막습니다. 실행기 수신 유효시간(기본 30분)은 그대로 적용됩니다. 구형 직접주문 서버의 복구는 알림 전용이며 주문을 재실행하지 않습니다.

이 보장은 로컬에서 접수한 요청 ID 기준입니다. TradingView가 새 HTTP 요청으로 같은 신호를 여러 번 보내면 기존 신호 중복 판정과 계좌별 보유·미완료 주문 검사를 함께 적용합니다. Discord 응답 유실로 카드가 중복될 가능성까지 정확히 한 번으로 보장하지는 않으며, 카드 발송 여부가 주문 재실행을 결정하지 않습니다. PC 자체가 꺼져 수신하지 못한 신호는 복구할 수 없습니다.

## 증권사별 순서와 상태 카드

- 각 증권사는 독립된 직렬 작업 큐를 사용합니다. 같은 계좌의 주문·취소·예약·체결 대조 순서는 유지하고, 한투 61초 요청 제한 대기가 키움 다음 신호를 붙잡지 않습니다.
- 주기 작업은 중복 적재하지 않습니다. 일반 명령과 승인 접수는 증권사 응답 대기와 분리합니다. 승인 후에는 실제 승인 가능한 계좌를 즉시 알려주고 두 증권사가 각각 처리합니다.
- 보유현황·Stock-Briefing 동기화·체결 로그 전송은 주문 큐 밖에서 처리합니다. 동기화 완료 표시는 조회 시작 때의 체결수량까지만 반영하여 더 늦은 체결을 누락시키지 않습니다.
- `주문승인`에 요청 ID별 `신호별 주문 진행` 카드 하나를 유지합니다. 계좌별 수신·승인 대기·예약·접수·부분체결·완료·차단·만료를 편집하며 다음 확인 시각과 유효기한도 보여줍니다. 접수된 주문의 체결 수량·잔량·가격은 주문 기록에서 읽습니다.
- 같은 카드에 `둘다`, `키움만`, `한투만`, `안 사`로 답장할 수 있습니다. 승인 만료·계좌 조건·중복 주문 검사는 생략하지 않습니다. 체결로그·매매일지는 기존 감사 기록으로 별도 유지합니다.
- 재시작 시 `SUBMITTING`/`UNKNOWN`이면 증권사 대조 전 자동 재주문하지 않습니다. 수신/주문 상태 파일도 원자 교체 후 디스크 동기화합니다. 파일은 동일 경로에서 실행하는 프로세스 하나만 쓰며 기존 단일 실행 잠금을 유지합니다.

휴장·조기 폐장과 갱신 대상은 [거래소 캘린더](./market-calendar.md)를 참고합니다.

## 실제 성과와 차단 신호

기존 `자동매매 누적 성과`를 유지하고 포트폴리오에 `자동매매 전략 비교` 카드를 추가합니다. `!account performance` 또는 `계좌 전략 성과 보여줘`는 요약 카드와 전체 JSON 자료를 반환합니다.

- 계좌·모의/실계좌·통화를 구분하고 최초 진입의 시간봉, 신호 코드, Sigma 구간, 정책 버전으로 분류합니다. 피라미딩에서 정책·시간봉이 섞이면 혼합/미확인으로 표시합니다. 과거 누락값을 현재 정책으로 채우지 않습니다.
- 실제 양수 체결수량만 사용합니다. 부분체결 후 취소·만료도 포함하며 자동매매 잔량이 0이 된 거래 주기만 승패로 계산합니다. 신호만 뜨거나 주문만 접수된 경우는 매매 성과가 아닙니다.
- 기본 손익·승률·수익률은 거래비용 전입니다. 수익률 분모는 완료 매매의 원가 합계이며 계좌의 기간 수익률이 아닙니다. 실현손익 낙폭은 완료 매매 누적손익의 고점 대비 하락액이며, 미실현 평가손익을 포함한 계좌 MDD가 아닙니다. 시각이 없으면 낙폭도 미확인입니다.
- 주문에 검증된 `executionCosts = { fees, taxes, currency, filledQuantity, source }`가 있으면 거래비용 차감 손익·수익률·승률을 계산합니다. 금액은 0 이상의 숫자, 통화와 증빙 대상 체결수량은 주문과 일치해야 합니다. **현재 브로커 응답 매핑은 이 비용 증빙을 자동 수집하지 않습니다.** 과거 거래비용을 0으로 채우지 않으며 하나라도 미확인이면 해당 그룹의 순성과는 미확인입니다. 확정 증빙 입력/수집 없이는 비용 차감 후 수익성을 판정할 수 없습니다. 연간 양도소득세 계산은 포함하지 않습니다.
- 실제 체결가를 사용하므로 슬리피지는 실제 손익에 이미 반영됩니다. 전체 자료의 `signalPriceDifference`는 신호가 대비 체결 차이(불리하면 양수)이며 지연 중 가격 변화도 포함합니다. 이를 수익에서 다시 빼지 않습니다.
- 계좌별 차단은 수신 상태의 `signals`에 사유와 정책을 저장합니다. 공통 게이트 차단은 기존 `trading-decisions.jsonl`에 시간봉·Sigma·정책 메타데이터를 보강해 저장합니다. 전체 자료에는 둘을 분리하며 같은 요청 ID의 공통 재평가는 마지막 결과만 셉니다. 차단 신호에 가상 체결가나 가상 승률을 부여하지 않습니다.

실거래 수익성, 실제 주문 종단간 검증, 기존 SE 잔고/과거 자동 보유 기록 불일치의 증빙 대조는 이 기능 완료와 별개입니다. 데이터를 임의로 수정하거나 손절 기준·과열 기준을 완화해 해결하지 않습니다.

## 검증

`npm run self-test`: 디스크 저장 전 ACK 방지, 저장 실패 503, 미전달/미처리 재시작 복구·만료·중복 방지, 증권사 지연 격리, Discord 장애 복구, 같은 카드 승인→접수 갱신, 휴장·조기 폐장·DST·다음 세션, 실제 체결/비용 미확인/차단 분리 계산을 가짜 증권사와 로컬 HTTP 서버로 검사합니다. 테스트가 실제 주문을 송신하지 않습니다.
