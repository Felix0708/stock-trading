# 운영 증빙과 외부 감시

2026-09-07 구현. 주문 조건을 완화하거나 실계좌를 해제하지 않는다. 신규 라이브러리·DB 없이 기존 계좌별 파일과 주문 작업 큐를 재사용한다.

## 구현과 실제 검증을 구분한다

| 항목 | 구현 | 실제 확인 / 남은 조건 |

## 계좌 증빙

실행기 시작 시 및 하루 간격으로 증권사 과거 체결·정산·자산을 조회한다. 실행기 소유자는 시스템/주문승인 채널에서 `!account reconcile`로 다시 대조할 수 있다. 이 명령은 주문·취소를 보내지 않는다.

- 수량이 모자란다는 이유만으로 매도를 만들어 넣지 않는다. 수동 매매·권리변동도 실제 증빙을 확인해야 한다.
- 연속 조회의 중간 페이지 실패, 날짜·주문번호 중복, 정정주문 체인, 미종결 잔량은 자동 수정하지 않는다.
- 실제 체결 증빙은 `<수신기록파일>.evidence.json`에 먼저 저장하고 주문 기록을 변경한다. 기록 수정 중 다른 갱신이 발생하면 다시 대조한다.
- 정산행은 종목·방향·일자·총체결수량·평단이 단일 주문과 일치할 때만 비용을 연결한다. 분할체결·일별 합산으로 구별되지 않으면 명세서가 필요하다.
- 한투 정산은 수수료와 실제 매매금액/정산금액 차이가 확인될 때 전체 비용으로 기록한다. 이미 체결가에 포함된 가격 차이를 손익에서 재차 차감하지 않는다.
- 총자산은 주문가능금액과 다르다. 자산곡선은 공식 평가 조회만 사용한다. 한투 대출 포함 계좌는 순자산 명세서 검증 전 제외한다.

### 모의 API 미지원 시 명세서 반영

`docs/account-statement.example.json`을 참고해 `<수신기록파일>.KIWOOM.statement.json` 또는 `.KIS.statement.json`을 로컬에 만든다. 현재 계좌·환경과 일치해야 하며, 증권사 화면/명세서에서 확인한 사실만 입력한다. 파일명 패턴은 Git에서 제외된다. 계좌번호·API 키는 넣지 않는다.

소유자가 `!account import`를 실행해야 반영한다. 파일을 만드는 것만으로 적용하지 않는다. 과거 실제 체결시각을 모르면 `filledAt: null`로 두며, 복구 시각을 체결시각으로 만들지 않는다. 명세서 `executionCosts`는 비용 전체가 확인될 때만 넣는다. `executions: []`로 입출금 전체 내역만 반영할 수도 있다.

입출금은 입금 양수/출금 음수이며 외부 입출금만 적는다. 매매대금·배당·수수료를 입출금으로 빼면 수익률이 왜곡된다. 외화 범위에서는 환전 유입/유출도 해당 범위의 외부 흐름으로 취급한다. 시작·종료시각 사이의 **전체** 내역을 확인한 후에만 `cashFlowCoverage`를 넣는다. 무입출금 기간도 확인한 명세서가 있어야 한다.

`!account performance`의 계좌 자산 성과는 미실현 평가를 포함한 일별 표본의 연결 Modified Dietz 수익률/낙폭이다. 표본 2개와 그 사이 입출금 전체 증빙이 필요하다. 장중 MDD·전기간 최고 낙폭이라고 부르지 않는다. 국내/해외·통화·계좌/모의실전 범위를 합산하지 않는다.

## 알람 증빙

- `!alerts status`: 각 종목·시간봉의 확인일, 만료일, 최종 수신 기록 내려받기.
- `!alerts verify NASDAQ:NVDA 240 알람ID 2026-10-01`: 소유자가 화면에서 확인한 활성 알람과 만료일 등록. 무기한일 때만 `never`.
- 확인 후 7일이 지나면 재확인 대상으로 표시한다. 이는 Discord 표시 정책이며 TradingView의 실제 만료일을 바꾸지 않는다.
- `.runtime/tradingview-alert-verification.json`: 브라우저 화면에서 읽은 활성 목록의 로컬 증빙. 종목 거래소가 유일하게 연결될 때만 적용한다. 화면상 Active 확인은 웹훅 전달 성공을 뜻하지 않는다.
- 새 수신은 별도 마지막 수신시각을 갱신한다. 무신호가 장애라는 추측으로 알람을 재생성하지 않는다.
- TradingView 알람은 생성 당시 스냅샷이므로 지표/입력 변경이 기존 알람에 자동 반영되지 않는다. [공식 알람 문서](https://www.tradingview.com/pine-script-docs/faq/alerts/#if-i-change-my-script-does-my-alert-change)

## 외부 감시 연결

`.github/workflows/external-health.yml`은 매시 2분부터 5분 간격으로 GitHub 실행기에서 점검한다. 주문 경로가 아닌 `/health`만 호출하며, 계좌/토큰/잔고를 로그나 공개 이슈에 넣지 않는다. 신호 서버의 Discord 연결과 등록된 계좌 실행기 상태도 점검 대상이다. 신호 서버가 계좌중립 모드인데 계좌 실행기 상태 파일이 하나도 없어도 비정상 처리한다.

GitHub 비밀값은 `MONITOR_HEALTH_URL`, `MONITOR_DISCORD_WEBHOOK` 두 개뿐이다. 시스템상태 채널의 알림 전용 웹훅이며 전체 봇 토큰과 증권사 키를 GitHub에 저장하지 않는다. 저장소 `issues:write`는 공개 이슈에 일반적인 장애/복구 상태만 기록하기 위해 사용한다. 반복 장애 시 이슈 하나를 유지하고 알림을 반복하지 않는다. 알림 응답이 유실되면 다음 실행에서 재전송될 수 있다.

로컬 봇에 해당 채널 웹훅 관리 권한이 이미 있다면 `node --env-file=.env.signal scripts/setup-external-monitor.cjs <채널ID> <소유자/저장소>`로 설정할 수 있다. 권한이 없다면 서버 소유자의 Discord 화면에서 전용 웹훅을 생성하고 GitHub Actions secret으로 넣는다. 봇의 서버 전체 권한을 넓힐 필요는 없다. `notify_test=true` 수동 실행은 실제 장애가 아니라는 문구로 알림 전송만 검증한다.

예약은 [GitHub 공식 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)상 지연/누락될 수 있고, 공개 저장소에 60일간 활동이 없으면 비활성화될 수 있다. 정확한 실시간 SLA가 필요해지면 독립 감시 서비스를 추가해야 한다. **이 기능은 중단 통지이지 손절 주문이 아니다.**

## 정책 고정과 주문 없는 후보 관찰

실계좌 읽기 전용 점검은 그대로 가능하다. 실제 주문이 가능한 실행기 시작에는 기존 실계좌 잠금 해제뿐 아니라 `ACCOUNT_APPROVED_POLICY_HASH`와 현재 정책 코드/위험설정 지문 일치도 필요하다. 변경된 지문을 자동으로 승인하지 않는다. 기존 모의계좌 설정은 바꾸지 않는다.

`forward-policy-study.json`은 배포 후 새 신호만 기록한다. 과거 웹훅 복구/재전송은 새 실험으로 사용하지 않는다. 현재 비교는 실계좌 Sigma 2.5 상한과 모의계좌 3.5 상한의 **진입 필터 관찰 연구**다. 다른 조건은 같은 신호에서 고정하고, 다음 동일 종목·시간봉 신호까지 가격 변화를 기록한다. 현금·수량·체결·부분매매를 시뮬레이션하지 않으므로 전체 전략 기대수익/승률로 해석해서는 안 된다. 거래가 발생한 실제 성과와 별도 자료로 제공한다.

## 손절 보호를 완료하려면

키움 미국주식 REST 매도 API의 `trde_tp=35 STOP`, `34 STOP LIMIT`, `stop_pric`는 [공식 ust20001 명세](https://openapi.kiwoom.com/m/guide/apiguide/38/ust20001)에 있다. 그러나 요청 필드 존재만으로 해당 계좌/세션의 지원, 주문 유효기간, Mac 중단 후 유지·발동, 부분매도 후 보호수량 갱신을 검증했다고 볼 수 없다.

완료 조건은 실제 계좌별 지원 확인 → 별도 승인한 소액 보호 주문 접수/조회/취소 검증 → 일반 매도 전 보호 주문 취소 확인 → 부분체결·응답유실·만료 후 보호수량 재조정 검증이다. 보호 주문이 체결되는 도중 일반 매도가 중복 전송되지 않아야 한다. 한투 해외주식의 동일 기능은 별도 확인 대상이다. 이 작업은 모의 운용 데이터 축적 후 실주문 검증에 대한 별도 승인이 필요하다는 기존 원칙을 유지한다.

## 검증

`npm run self-test`에 증빙의 정확/모호 연결, 오래된 기록 덮어쓰기 차단, 비용 미확인, 연속조회 실패, 입출금 조정, 알람 증빙 만료, 실계좌 정책 지문, 재생 신호 제외, 외부 장애/복구·중복 알림 방지 검증이 포함된다. 이 자동검증은 테스트 데이터이며 실제 브로커 주문을 보내지 않는다.
