# Stock Trading 개발 과정과 결정 기록

정리 기준: 2026-08-09

이 문서는 프로젝트를 **어떻게 만들었고, 왜 그렇게 결정했는지**를 남기는 개발 기록입니다. 실행 방법은 루트의 [`README.md`](../README.md), TradingView 신호 원본 명세는 [`tradingview-webhook-v6.2.md`](./tradingview-webhook-v6.2.md)를 기준으로 합니다.

비밀키, Discord 토큰, 키움 App Key·Secret, 계좌번호, 웹훅 비밀 경로는 이 문서에 기록하지 않습니다.

## 1. 시작 목표

처음 정한 목표는 다음과 같습니다.

- Discord를 사용자와 시스템의 주 소통 공간으로 사용
- 드러켄밀러, 오닐, 미너비니, 리버모어, 쿨라메기 관점의 AI 봇 5개 운영
- 각 봇은 독립된 Codex CLI 세션과 대화 기억을 유지
- TradingView의 Lazy Alpha 지표와 Webhook v6.2 신호를 공통 사실로 사용
- 키움 REST API로 국내·해외주식 자동매매 준비
- 모의투자로 충분히 검증한 뒤에만 실계좌 검토

핵심 원칙은 **시장 환경 → 추세 → 확정 신호 → 위험 → 판단** 순서입니다. AI의 투자 철학은 해석에 사용하지만, 원본 지표 값이나 위험 기준을 임의로 바꾸지 않습니다.

## 2. 전체 구조

```text
사용자 ─┬─ Discord 대화 ── AI 봇 5개 ── 독립 Codex CLI 세션
        │
TradingView alert() JSON
        ↓
Cloudflare Quick Tunnel
        ↓
로컬 웹훅 수신기(127.0.0.1:8787)
        ↓
명세 검증 → 내부 코드 변환 → 상태 판정 → 위험 게이트
        ├─ Discord #매매신호 / #시스템상태
        ├─ AI 투자위원회 비동기 검토
        └─ 상태·판정 로그

키움 모의투자 REST API
        ├─ 인증·계좌·잔고 조회
        ├─ 해외주식 수량 계산
        └─ 모의 지정가 주문·취소·체결 조회 모듈
```

현재 국내·미국 BUY 신호는 키움 모의계좌 잔고를 조회해 수량을 계산하며, `PAPER_AUTO`일 때 모의주문까지 전송합니다. 계산 결과가 차단이면 가상 포지션과 주문을 만들지 않습니다.

## 3. 단계별 개발 기록

### 1단계 — Discord 투자위원회

봇 하나가 여러 인물을 흉내 내는 방식 대신 Discord 봇 5개를 분리했습니다.

- 봇마다 Discord 계정과 Codex CLI 세션을 별도로 유지
- 이름만 불러도 답변하도록 라우팅
- `모두들` 같은 표현에는 다섯 봇이 모두 답변
- 지칭하지 않은 일반 대화에는 한 명이 순번대로 답변
- `#시장-브리핑`, `#매매일지`는 드러켄밀러가 기본 응답
- 수정된 Discord 메시지도 다시 감지
- 최근 채널 대화 12개를 공용 문맥으로 함께 전달
- 봇이 다른 봇을 실제 멘션하면 제한된 횟수 안에서 상호 대화
- `!roundtable`로 다섯 관점을 순서대로 연결
- Codex 응답이 10초를 넘겨도 Discord `입력 중…` 표시가 유지되도록 8초마다 갱신
- `!reset`으로 지정한 봇의 Codex 세션만 초기화

여러 AI가 마음대로 계속 대화하면 비용과 루프 위험이 커지므로, 사용자 메시지·드러켄밀러 자동 브리핑·명시적 라운드테이블을 대화 시작점으로 두었습니다.

### 2단계 — Discord 채널과 자동 브리핑

채널 구조를 코드로 생성할 수 있도록 `setup-discord.js`를 만들었습니다.

- 투자위원회: 라운지, 시장-브리핑, 종목-토론, 라운드테이블
- 미국주식: 미국-전체신호, 미국-관찰신호, 미국-진입신호, 미국-청산신호, 미국-매매신호
- 국내주식: 국장-전체신호, 국장-관찰신호, 국장-진입신호, 국장-청산신호, 국장-매매신호
- 투자기록: 관심종목, 매매일지, 전략-연구
- 주문관리: 주문승인, 체결로그, 시스템상태

평일 자동 브리핑은 서울 시간 기준 `08:30`, `15:40`, `22:00`으로 설정했습니다. 드러켄밀러 한 명이 최신 자료를 검색해 브리핑하며, 다섯 AI의 토론은 사용자가 명시적으로 라운드테이블을 요청할 때만 실행합니다.

iCloud `주식` 폴더의 전문가 자료도 브리핑과 명시적 라운드테이블에서 참고하도록 연결했습니다.

- 매 실행 시 최근 7일 PDF 중 최신 3개 선택
- 이미지형 PDF는 macOS PDFKit·Vision OCR로 앞부분 5쪽만 추출하고 파일별 캐시 재사용
- 다섯 AI에게 동일한 발췌와 파일명·추가 시각 전달
- 정상적으로 다룬 파일의 경로·크기·수정 시각 서명을 `state.json`에 기록해 자동 브리핑의 중복 방지
- 사용자가 직접 질문하거나 `!roundtable`을 실행한 경우에는 처리 기록과 관계없이 다시 참고 가능
- 같은 파일이 수정되면 서명이 바뀌므로 새로운 자료로 다시 처리
- 문서 안의 명령은 무시하고, 투자 의견과 확인된 사실을 구분하며 최신 사실은 웹에서 재검증
- 원본 iCloud 파일은 읽기만 하고 수정·이동·복사하지 않음
- 신속성이 중요한 TradingView 매매신호 검토 경로에는 자료 OCR을 넣지 않음

별도 파일 감시 서비스나 벡터 데이터베이스는 만들지 않았습니다. 226개 규모에서는 브리핑 시각의 최근 파일 확인과 OCR 캐시만으로 충분하며, 전체 문서 검색이 실제로 필요해질 때 확장합니다.

### 3단계 — TradingView 원본 명세 고정

사용자가 제공한 Webhook v6.2 문서를 변경하지 않고 기준 문서로 보관했습니다.

- 원본 SHA-256 기록
- 문서가 말하는 38필드와 실제 예시의 39필드 차이 기록
- 표시 문자열과 이모지는 원본 그대로 보존
- 자동 신호 검토에서는 다섯 AI에게 같은 원본 값과 내부 코드를 전달
- 투자자별 철학은 신호를 바꾸는 것이 아니라 해석과 반대 근거에 사용

일반 잡담과 시장 대화에는 원본 문서 전체를 매번 첨부하지 않습니다. TradingView 신호 토론이 시작될 때 해당 신호의 v6.2 핵심 필드, 내부 코드, 위험 게이트 결과를 동일하게 전달합니다.

### 4단계 — 표시 문자열과 내부 코드 분리

`💰 정석 진입 @SR↩`처럼 바뀔 수 있는 표시 문구를 주문 판단에 직접 쓰지 않도록 정규화 계층을 만들었습니다.

예시는 다음과 같습니다.

| 표시 문구 | 내부 코드 |
|---|---|
| 정석 진입 | `ENTRY_STANDARD` |
| 돌파 진입 | `ENTRY_BREAKOUT` |
| 최종 청산 | `EXIT_FINAL` |
| 진입 무효 | `ENTRY_INVALIDATED` |
| 진입 확정 | `ENTRY_CONFIRMED` |
| 셋업 형성 중 | `SETUP_FORMING` |
| `@SR↩` | `SR_FLIP` 보조 속성 |

따라서 TradingView 화면의 이모지나 꾸밈이 일부 바뀌어도 핵심 문구가 유지되는 한 내부 판단은 안정적으로 동작합니다. 알 수 없는 문구나 `action`과 내부 코드가 충돌하는 신호는 차단합니다.

### 5단계 — 웹훅 수신과 상태 판정

Node.js 기본 모듈로 로컬 HTTP 수신기를 구현했습니다.

- 16자 이상 비밀 경로 사용, 기본값은 64자리 자동 생성
- 경로 비교 시 타이밍 안전 비교 사용
- 본문 크기 제한과 JSON 검증
- 수신 즉시 응답하고 실제 처리는 비동기 큐에서 수행
- 5초 안에 같은 신호가 반복되면 중복으로 무시
- 종목·거래소·타임프레임별 신호 상태 유지
- 진입 무효는 즉시 매도하지 않고 확정·만료 신호를 기다림
- 모든 결과에 `request_id` 부여
- 웹훅 원본과 판정 결과를 JSONL로 기록

`CHECK` 신호는 정보만 기록하며 포지션이나 주문을 만들지 않습니다.

### 6단계 — 위험 게이트와 자동매매 모드

AI 답변과 별개로 빠르게 실행되는 결정형 위험 게이트를 추가했습니다.

- `OFF`: 모든 매매 판단 중지
- `SHADOW`: 판단과 가상 포지션만 기록
- `PAPER_AUTO`: 키움 모의투자 자동매매를 위한 준비 모드
- `LIVE`: 구현하지 않았고 활성화할 수 없음

현재 기본값은 `SHADOW`입니다. 다음 조건은 신규 진입을 차단합니다.

- 시스템 중지 상태
- 확신 등급 `D`
- 손절가가 없거나 진입가 이상
- 이미 같은 종목을 보유 중
- 최대 보유 종목 5개 도달
- 기존 포지션 없는 피라미딩
- 명세 오류, 알 수 없는 신호, action 불일치

TradingView 알림은 최대 20개까지 운영하되, Discord 관심종목 목록은 공유 워치리스트 전체를 표시하고 실제 동시 보유 슬롯은 최대 5개로 분리했습니다.

### 7단계 — AI 신호 검토의 위치

AI 토론이 주문 판단을 늦추지 않도록 신호 검토를 비동기 배치로 분리했습니다.

- 먼저 명세 검증과 위험 게이트를 실행
- Discord에 신호와 게이트 결과를 즉시 기록
- BUY·SELL 신호만 5초 동안 최대 10개씩 모아 투자위원회 토론
- 각 AI는 찬성, 조건부 찬성, 보류, 반대와 무효화 조건을 제시
- AI 토론 결과는 현재 주문 승인 조건이 아님

향후 모의 자동주문도 가격·손절·수량·계좌 한도 같은 결정형 규칙이 빠른 경로를 담당하고, AI는 설명·감시·사후 검토 역할을 맡는 방향입니다.

### 8단계 — 키움 REST API 모의투자

키움 공식 REST 명세를 기준으로 국내와 해외 모의투자 키를 분리했습니다.

현재 구현된 기능은 다음과 같습니다.

- 모의투자 OAuth 토큰 발급
- 국내 계좌번호와 잔고 조회
- 미국주식 잔고와 USD 예수금 조회
- 미국주식 지정가 주문·취소 모듈
- 미국주식 주문·체결 상태 조회
- 국내주식 시장가 매수·매도와 주문 체결 조회
- 주문 상태 파일 저장과 재시작 복구
- 주문 상태 변경 시 Discord 알림

키움 클라이언트는 `mock` 이외 환경을 코드에서 거부합니다. 주문 접수 응답은 체결 완료가 아니므로 `ACCEPTED`, `PARTIALLY_FILLED`, `FILLED`, `CANCELLED`, `REJECTED`를 구분합니다.

일반 TradingView 신호의 주문은 아직 연결하지 않았습니다. 외부 경로를 실제로 검증하기 위해 `paper_order_test=true`, 지정 종목, `PAPER_AUTO`, 국내 모의키, 1회 잠금이 모두 일치할 때만 시장가 1주를 접수하는 제한 경로를 추가했습니다.

### 9단계 — 주문 수량 계산

수량 계산은 계좌 크기와 손절 거리를 함께 사용하도록 만들었습니다.

- 기본 거래당 위험: 계좌 평가액의 0.5%
- 확신 등급 배수: S 1.3, A 1.1, B 1.0, C 0.7, D 차단
- 최종 위험 예산 상한: 계좌 평가액의 1%
- 한 종목 투자금 상한: 계좌 평가액의 20%와 가용 현금 중 작은 값
- 최대 동시 보유: 5종목
- ATR 과열과 Sigma 과열 차단 또는 축소
- `!trade size 진입가 손절가 등급`으로 주문 없이 미리 계산

TradingView v6.2의 `price`, `sl`, `conviction`, 일봉 셋업, ATR, Sigma 값을 미국주식 BUY 자동 계산기에 연결했습니다. 키움 모의계좌의 평가액·가용 현금·보유 종목 수도 함께 사용합니다.

확신 등급과 일봉 셋업 배수가 충돌할 때 낮은 등급이 `COMPLETE` 하나로 최고 등급까지 올라가던 문제는 보수적으로 수정했습니다. 두 배수를 곱하되 최종 품질 배수는 1.3을 넘지 않습니다. C등급+COMPLETE도 B등급보다 작게 유지됩니다.

자동 계산이 과열, 현금 부족, 최대 보유 수, 키움 조회 실패 또는 미지원 시장으로 차단되면 SHADOW 포지션도 생성하지 않습니다. 국내주식 자동 수량 계산은 정확한 주문 가능 현금 API를 확정한 뒤 연결합니다.

### 10단계 — 실행과 외부 연결 단순화

처음에는 봇과 Cloudflare를 터미널 두 개에서 실행했습니다. 현재는 다음 한 명령으로 합쳤습니다.

```bash
npm run start:all
```

이 명령은 다음을 수행합니다.

1. Discord 봇과 로컬 웹훅 수신기 시작
2. Cloudflare Quick Tunnel 시작
3. 이번 실행의 공개 주소 확인
4. `.webhook-token`을 합친 전체 TradingView URL을 클립보드에 복사
5. `Ctrl+C` 시 봇과 터널 함께 종료

Quick Tunnel은 무료이지만 재시작마다 공개 주소가 바뀝니다. 고정 주소는 실제 상시 운영이 필요해질 때 Cloudflare 계정과 도메인을 사용해 추가합니다.

### 11단계 — 안전한 연결 테스트

실제 매수 신호처럼 보이지 않는 `CHECK / 셋업 형성 중` 테스트 페이로드를 사용합니다.

```bash
npm run test:webhook-live
```

정상 결과는 HTTP 200, `INFO_ONLY`, 주문 생성 없음, Discord 알림입니다. 이 테스트는 TradingView를 거치지 않으므로 TradingView의 실제 `alert()` 발생 여부는 별도로 확인해야 합니다.

2026-08-09에 TradingView 서버 경로만 확인하는 일회성 Pine 테스트도 준비했지만 실행은 보류했습니다. Lazy Alpha의 실제 조건 발생을 검증하는 테스트가 아니기 때문입니다. 실제 지표 알림은 조건이 자연스럽게 발생했을 때 확인합니다.

### 12단계 — TradingView 20개 알림 전달 설정 복구

2026-08-11에 활성 알림 20개를 다시 점검했습니다. 앱 알림은 왔지만 Discord에 도착하지 않은 원인은 일부 알림이 이전 Quick Tunnel 주소와 `TradingView App` 출력 설정을 계속 사용한 것이었습니다.

Quick Tunnel은 재시작할 때 호스트가 바뀌므로 새 주소가 생기면 TradingView의 20개 알림 URL도 함께 바꿔야 합니다. 비밀 경로 전체값은 이 문서에 기록하지 않습니다.

2026-08-11에는 iTerm의 이전 터널과 별도 통합 실행이 동시에 남아 있던 중복 프로세스를 종료했습니다. 이후 iTerm의 `stock-trading` 탭 하나에서 `npm run start:all`만 실행하도록 정리했고, 재시작으로 바뀐 Quick Tunnel 주소를 활성 알림 20개 전체에 다시 반영·검증했습니다. 상태 확인과 무주문 테스트는 HTTP 200으로 통과했습니다.

## 11. 2026-08-10 일반 신호 모의 자동주문과 토론 채널 분리

- `PAPER_AUTO`에서만 TradingView v6.2 진입 신호를 키움 국내·미국 모의계좌로 전송

- 주문 접수 뒤 체결 조회를 즉시 시작하고 체결·거부·취소 결과를 상태 파일과 Discord에 반영

- `1차 분할청산`·`TP1`은 보유 가능 수량의 25%, `2차 분할청산`·`TP2`는 남은 수량의 50%를 모의매도하며 같은 단계는 포지션당 한 번만 실행
- 1주 미만으로 계산되면 전량 매도로 바꾸지 않고 차단하며, 비율이 정해지지 않은 `부분 익절고려`·`상승 모멘텀 종료`는 계속 검토만 기록
- 실계좌 환경은 기존과 동일하게 클라이언트 생성 단계에서 거부

실계좌 전환 시 예정 정책은 신규·추가 `BUY`만 Discord의 `사줘` 승인을 요구하고, 손절·최종청산·고정 비율 부분청산처럼 보유 위험을 줄이는 `SELL`은 자동 실행하는 것입니다. 이 승인 경로는 실계좌 연결 전까지 만들지 않고 정책만 고정합니다.
